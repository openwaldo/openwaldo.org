howto · waldo compose

One document, one build.

What this HOWTO does: builds a model from a single YAML compose document — architecture plus the staged curriculum — with a strict pre-flight check, resumable stages, and a bill of materials recorded per stage. This is how you keep, share, and re-run a build. The document is intent; the BOM each stage records is the outcome.

Prerequisites are the same as WALDO build: the waldo binary, a checkout of the index, and uv. Do the direct path once first — it shows what this document is a shorthand for.

step 1

Write the document

waldo compose new my-model.yaml writes a template documenting every field in the schema with its default — and run inside a checkout, it lists that tree’s corpus paths as comments so you can pick from them. In brief:

my-model.yaml
model: bookworm

arch:
  preset: 10m            # or params: 500m, or every dimension spelled out
  context: 512
  # tokenizer: byte      # byte | tiktoken/<encoding>

train:
  seed: 42
  checkpoint_steps: 500
  stages:
    - phase: pretrain    # pretrain, then midtrain as an anneal
      paths: [core/books]
      epochs: 1          # or steps:, or tokens: — exactly one
      batch: 8
      lr: 3e-4
step 2

Check before you build

check is the command that saves money. It parses strictly (an unknown key is an error, never a silent default), reports data starvation and budget coverage, forecasts wall-clock against real hardware, sizes the optimizer state against this machine’s memory — and inspects the model the document targets. Architecture is immutable after init, so a mismatch is a build that would fail after you queued it; check names the differing dimension instead.

compose check
$ waldo compose check configs/words373m.yaml
model words373m: 24 layers, 1024 hidden, vocab 100277 (tiktoken/cl100k_base) — ~373.3M params
pretrain: core — 228881 steps, batch 32, lr 0.0003

projected build (≈6 × params × tokens-seen = 16.8 EFLOPs; rough ±2×):
  Apple M4 Max (MLX, 128 GB unified) ~32.4 days
  1× H100 80GB                       ~13.3 hours
  1× AMD MI300X 192GB                ~11.7 hours
  8× H200 (one node, DDP)            ~1.7 hours

room (fp32):
  weights on disk                    ~1.4 GB
  training state in memory           ~5.6 GB (weights + gradients + Adam moments)
  this machine                       431.6 GB free disk, 128.0 GB memory

projected quality after this training: held-out confidence ~5.56% (loss ~2.89)
ok
step 3

Build

A build creates the model from scratch and refuses one that already has training, because appending to a run history someone will later read as provenance is a different intention. To continue an interrupted run, --append — completed stages are skipped, so it resumes from the first incomplete one. Editing one stage reruns only that stage; pass a name to build the same curriculum as a different model: waldo compose build variant-b configs/words373m.yaml.

compose build
$ waldo compose build configs/smoke10m.yaml
created smoke10m: 6 layers, 384 hidden, 6 heads (2 kv), ffn 1024, context 128,
  vocab 259 (byte) — ~9.5M params
=== pretrain (1/1): core/common-pile/public-domain-review (20 steps, backend mlx) ===
done: final loss 3.2203 (held-out 3.1666)
train complete: smoke10m (1 stage(s) run), BOM-pinned

# resume an interrupted run — completed stages are skipped
$ waldo compose build --append configs/english1b.yaml
pretrain: up to date, skipping
=== midtrain (2/2): post-train (508 steps, backend pytorch) ===

# single-node multi-GPU is turnkey
$ waldo compose build configs/words373m.yaml --gpus 8

The ladder

WALDO checks a compose before execution, forecasts its resource needs, and records the resolved architecture, corpus, backend, and training parameters. See the current model workflow for the supported commands, backends, and present limits.
