the contributing walkthrough

The contribution is a git commit.

How a corpus gets into OpenWALDO. Shard bytes go to a lookaside store you host; what you open a pull request with is small, reviewable metadata: what the data is, where it came from, what license it carries, and the hash of every byte of it.

Every command and every line of output below is real, from a run of exactly these steps. If you want to train a model instead, see the training walkthroughs.

step 0

What you need

toolchain

waldo + git

A release build of waldo, or make install from source (Go 1.24+) — and git, because the contribution is a commit.

network

A fast connection

You are moving a corpus, not a config file: the raw fetch comes down, and every shard byte goes back up to the store you host.

storage

Lots of disk

Raw data, converted shards, and a local copy of your lookaside store all live here at once — plan for several times the size of the data you’re bringing.

step 1

Stand in an index checkout

The checkout is the tree. Commands resolve against the checkout you are standing in, climbing to its root the way git does, so core/books means the same thing from anywhere inside it.

the index
$ git clone https://github.com/openwaldo/waldo-index.git && cd waldo-index

# or start a private tree instead — same toolchain, nothing published
$ waldo index init tree
initialized …/tree as an index root — ingest data with `waldo ingest <raw> <path>`
step 2

Point at a lookaside store (once per machine)

Shard bytes never live in git. For a first pass a local directory is fine; for real hosting it is an S3 bucket plus a one-time waldo lookaside login — after which uploads are automatic and reads never need credentials at all.

lookaside
$ waldo lookaside set ~/waldo-store --url https://data.example.org/lookaside
lookaside store set to /Users/you/waldo-store

The --url is the public face the manifest records. It is what a stranger will fetch from, so it has to be the address the bytes will really be reachable at.

step 3

Get raw data

Ingest takes any local directory — and assembling it is your job. Pull from an API, mirror an archive, dump a knowledge base, gather documents you already have: plain text, Markdown, JSONL, HTML, or EPUB, with the format sensed per file. How you fetch is up to you; the only interface is what lands on disk.

Hints, for fetching from a public source: curl and jq go a long way, and the toolchain’s fetchers/ directory holds shell scripts that pull specific public sources — worked examples to crib from, outside the binary and outside the deterministic core. Prefer the primary source, and mind the license of the underlying documents — that’s what you’ll be attesting to in step 5.

If you want your fetch to be reproducible by the next person, write a fetch-log.json — the metafile. Write it last and atomically, so its presence is the signal that the fetch finished. It declares how to read every file, and may propose what the corpus is:

fetch-log.json
{
  "kind": "fetch-log", "tool": "gutenberg.sh", "order": "as-listed",
  "source": { "name": "gutenberg", "origin": "Project Gutenberg (gutenberg.org)",
              "version": "2026-08-03 catalog", "url": "https://www.gutenberg.org/" },
  "corpus": { "title": "Project Gutenberg",
              "description": "Public-domain books transcribed and proofread by …",
              "license": "CC0-1.0" },
  "defaults": { "content_type": "text" },
  "files": [ { "name": "00001-pg1342.txt", "url": "…", "sha256": "…" } ]
}

The metafile contract is documented in fetchers/README.md — normative if you write one, and entirely optional: ingest takes a directory without one and asks you for what’s missing. Two rules from it are worth knowing before you start. The file list is sorted by content hash, not by fetch order, so two people who fetch the same documents produce the same corpus even if they arrive in a different sequence — order that depends on the environment is not order. And a metafile does not say where its corpus goes. There is no destination field and there cannot be: where a corpus belongs in the tree is a curation decision about the namespace, and a fetcher pulls from upstream.

step 4

Ingest

The second argument is required. No metafile proposes a destination, so you say where the corpus lands. The manifest’s filename follows it: core/mine holds mine.json. Deep paths are created on demand, each with a generated index.json, and the new entry is listed in its parent.

Ingest needs four things to name a corpus — name, title, description, license. The name comes from the destination; the other three come from you via --title --description --license, or from the metafile if yours declared them. It will not guess, and a non-interactive run stops rather than inventing them. With no metafile, --source declares provenance by hand:

ingest — your own data
$ waldo ingest /tmp/mydata core/mine \
      --title "My Corpus" --description "One sentence saying what this is." \
      --license CC-BY-4.0 \
      --source "name=mine,origin=My Archive,version=2026-08,url=https://example.org/,sha256=…"

The run below is the fully worked example this page’s numbers come from — six Project Gutenberg books fetched with the gutenberg.sh fetcher script, whose metafile declares title, description and license, so the ingest passes no flags at all:

ingest — with a metafile
$ waldo ingest /tmp/raw core/books
converting /tmp/raw with metafile...
  converted 6 documents (2.2 MB, 510.0K tokens; avg 373.2 KB, 85005 tokens/doc)
packing (budget 536870912 bytes)...
  staged shard 87f1a41d56b5 (CC0-1.0, 6 docs, 2.2 MB raw)
  [1/1] pushed 87f1a41d56b5 (2.5 MB in 0.0s)
summary: 6 docs, 510031 tokens | 2.2 MB text → 2.5 MB parquet | 1 shard(s) | 1 uploaded

ingested 6 docs (510031 tokens) into 1 shard(s): 1 uploaded, 0 already hosted
manifest: …/core/books/books.json

Useful flags: --purge removes the raw directory once the corpus is real, and --offline converts, packs and stops — for a machine that can reach its upstream but not the store. waldo ingest push finishes it later from somewhere with a route.

step 5

Verify, then commit

verify re-derives every index.json and byte-compares it, then validates every manifest. By default it also confirms the store holds what the index claims — a HEAD per shard, nothing downloaded — and --fetch downloads and re-hashes everything.

verify
$ waldo index verify core/books --offline
core/books                    index     ok
core/books/books.json         manifest  ok — 1 shard(s), 6 docs, 510.0K tokens
checked: 1 index(es), 1 manifest(s); declared 1 shard(s), 6 docs, 510.0K tokens
ok

# without --offline, verify checks the committed URL really resolves —
# this walkthrough set a placeholder, so it refuses, correctly:
$ waldo index verify core/books
core/books/books.json ⇒ 87f1a41d56b5  shard  MISSING: Head "https://data.example.org/…":
    dial tcp: lookup data.example.org: no such host
error: 1 problem(s) found

That error is not a bug to work around — it is the tool refusing to certify a corpus nobody else can fetch. Before you open a pull request, the committed URL must really resolve, and the un-flagged verify is what proves it.

commit — this is the contribution
$ git add . && git commit -s -m "Add Project Gutenberg starter corpus"

The -s is the point. It is the DCO sign-off — your attestation, under your git identity, that you have the right to contribute this data under the license you declared. In the shared-index workflow that commit is the contribution: push the branch and open a pull request against waldo-index. CI runs the same waldo index verify you just ran.

the bar

What makes a good contribution.

The index is a curated layer on top of the open-data commons, not a re-hosting of it. CORPUS-BACKLOG.md states the sourcing principles in full and lists what is wanted next, with runnable commands. The short version:

Add value

A corpus should be better here than it was upstream: single-license shards, deduplicated, tokenizer-counted, auditable. If upstream already ships it training-ready, reference it rather than duplicating the bytes.

Prefer the primary source

Fetching Harvard’s caselaw from Harvard beats fetching a repackage of it, so the index’s provenance reads as the institutions that published the data.

Label, do not exclude

If a work is freely distributable it belongs here — permissive, copyleft, share-alike, non-commercial alike — with the license recorded per record, so a downstream reader can choose. What stays out is anything with no grant to redistribute. Silence is not a grant.

determinism

Re-running is a no-op.

Ingest is deterministic. The same input produces the same shard hashes, so a second run uploads nothing and rewrites identical bytes. If something did change, the re-pack check says what — and distinguishes a different container from different contents. A change to what the corpus holds is reported as drift, loudly, because that is the case where “I just re-ran it” is not an explanation.

re-run
$ waldo ingest /tmp/raw core/books
  [1/1] 87f1a41d56b5 already hosted (2.5 MB)
re-pack: identical to git HEAD
ingested 6 docs (510031 tokens) into 1 shard(s): 0 uploaded, 1 already hosted
start here

The best time to join a commons is while it’s being built.

Questions about a source, a license, or a fetcher? Ask before you fetch — someone has probably hit it.
